# Skill review

The shared skill library is one catalog, one deployed tree, and seven clients
that discover it in three different ways. This document is the review
reference for that library: which client loads what, which rules decide the
selection and the ownership, and the checklist a reviewer applies to a skill
that is added or changed.

It is a review document, not a second specification. The decisions live in
[ADR 0013](adr/0013-single-owner-skill-library.md); the deployment behaviour
lives in [AGENT_PAYLOAD.md](AGENT_PAYLOAD.md); this document tells a reviewer
what to look at and what the check reports.

## The per-client matrix

The shared tree at `~/.agents/skills` is the portable home of the library. It
holds the selected profile and the generated Herdr skill. The clients differ in
how they discover it, and that difference is the reason three shapes exist.

| Client | Shape | Root | What it receives |
| --- | --- | --- | --- |
| Codex | shared tree | `~/.agents/skills` | the whole tree; the client has no supported persistent filter |
| Kimi Code | shared tree | `~/.agents/skills` | the whole tree; the client has no supported persistent filter |
| Qoder | shared tree | `~/.agents/skills` | the whole tree; the client has no supported persistent filter |
| Pi | shared tree | `~/.agents/skills` | the selected profile, registered as its profile root |
| OpenCode V2 | shared tree | `~/.agents/skills` | the selected profile, registered as its profile root |
| Claude Code | filtered copy | `~/.claude/skills` | the selected profile, copied as regular files |
| MiniMax Code | filtered copy | `~/.minimax/skills` | the selected profile, copied as regular files |

The matrix is the machine-readable form in
`deployment/agent-payload/skill-clients.tsv`, and the check prints it with the
number of skills each client loads: the profile count for a copy and for a
profile root, and the whole tree for a global reader. A shared-tree reader has
no managed root of its own.

Three consequences follow from the matrix:

- **A shared-tree reader has no root of its own.** Codex, Kimi, and Qoder read
  the shared tree directly. Pi and OpenCode read the same directory through
  their registered profile root, so no second copy of the profile is deployed
  for them.
- **A copy root holds the same profile.** Claude Code and MiniMax Code
  discover skills only in their own directory, so the deployment copies the
  selected profile there. The copy holds the same bytes as the shared tree.
- **A device root is never written.** Pi scans `~/.pi/agent/skills` and
  OpenCode scans `~/.config/opencode/skills` beside the registered root. The
  deployment owns neither: it reports a name that both roots provide and never
  writes there. A name belongs to one discovery root per client.

The generated Herdr skill is not a catalog row. Herdr ships its own
instructions, so the deployment writes them into the shared tree and refreshes
them from the installed binary. The same generated bytes reach every managed
copy root, and every root records the skill so the prune leaves it alone. It is
outside the catalog budget: the review names it and excludes it from the
ratchet, because its bytes come from the installed tool rather than a reviewed
catalog row. A reviewed exception can also name a tagged row that is not in the
current library; the check reports how many do and does not treat that as a
stale record.

## The selection rules

The catalog's last column decides what a host receives.

| Selection | Meaning |
| --- | --- |
| `auto` | the reviewed core; every host receives it |
| a tag | a group the host asks for: `lark`, `design`, `caveman` |

A host opts in with `DOTFILES_SKILLS=<tag>` or `DOTFILES_SKILLS=<name>`. The
selection applies to the fetch and to the copy into a managed root, so a
library supplied through `DOTFILES_SKILLS_DIR` deploys the selected skills and
nothing else. A name the catalog does not declare is device content: it never
enters a managed root, and it is never pruned.

`auto` is the reviewed core: the mattpocock engineering and productivity
skills, graphify, worktrunk, the humanizers, `show-me`, `pr` and `research`,
the caveman mode with its compress skill, and the six generic engineering
skills of the caveman repository. The other caveman-branded skills, the
diagram and slide-deck skills, and the Feishu skills stay behind their tags.

## The ownership rules

| Part | Owner | Rule |
| --- | --- | --- |
| Catalog and pins | `deployment/skills.tsv`, `deployment/skills.lock.tsv` | the repository owns the rows and the bytes that ship |
| Managed roots | the deployment | `~/.agents/skills`, `~/.claude/skills`, `~/.minimax/skills` |
| Managed skill inventory | device state | the directories the deployment wrote, per root |
| Generated skills | device state | the roots that hold them, so the prune leaves them alone |
| The `bunx skills` lockfile | the device | read and reported; never written |
| A device skill | the device | preserved and reported; never pruned |
| A skill collision | the device | preserved and reported; the deployment never writes through it |

The catalog is the only writer of a managed root. `bunx skills add` and
`bunx skills update` must not target a managed root: a second writer replaces
reviewed bytes with unpinned ones, and the next apply overwrites the change.
An entry added that way is reported as drift and named for removal.

Upstream prose is not rewritten. The lock's value is that the deployed bytes
are upstream's, so a skill that is too long is recorded as a reviewed
exception rather than edited.

## The review checklist

The questions below are derived from the upstream skill-authoring guidance.
They apply to a new catalog row and to a changed one.

1. **Is the description short?** A description is the trigger a client reads
   to decide whether the skill applies. It states what the skill does and when
   to use it, in one or two sentences, without the tutorial. A description
   that explains the workflow belongs in the root document.
2. **Is the root document a router?** The root document states what the skill
   does, when to use it, and the shape of the work. The detail lives in
   reference files that are read on demand. A root document that carries the
   detail forces every client to carry it in context.
3. **Is the instruction specific without being over-specified?** The skill
   says what to do and what must not change, and leaves the steps the model
   can derive to the model. A skill that spells out every command, every
   parameter, and every ordering stops the model from adapting it, and stops
   being true when the tools change.
4. **Does it fit the model that reads it?** The audience is an agent with
   tools, not a colleague at a desk. The instructions are written for the
   agent: no preamble, no encouragement, no restatement of the request, and
   no prose that only makes sense to a human reader.
5. **Is the context budget worth it?** Every skill in the profile costs every
   client its description, and the root document costs the clients that open
   it. A skill earns its place when it covers a workflow that the shared
   instructions do not already cover. When two skills cover the same ground,
   one of them leaves the profile.
6. **Does the row belong to this catalog?** The catalog owns global agent
   integration. A skill that belongs to one project, one account, or one
   machine is device content, not a catalog row.

## The budget and the ratchet

The check measures the library and applies two budgets:

| Budget | Limit | Exception |
| --- | --- | --- |
| Description | 240 characters | none |
| Root document | 200 lines | a skill that ships a reference file may be longer |

A folded (`>`) or literal (`|`) frontmatter description is read as its joined
prose, so a block description is measured as the text a client reads and not
as one long line.

Rows that are already above a budget are recorded as reviewed exceptions in
`deployment/skill-budget-exceptions.tsv`, with the measured description
length, the measured root lines, whether the skill ships a reference file, and
the reason the row stays. The ratchet has three rules:

- A row above a budget with no exception is new, and the check fails by name.
- A row whose measurements no longer match its exception changed, and the
  check fails by name. Updating an exception is a review action: the reviewer
  records the new measurements and the reason, or the row is brought back
  inside the budget.
- An exception for a row that is now inside the budget fails as well, because
  the record is stale.

## Migrating a pre-inventory device

A device that installed skills before the managed inventory existed has
directories the deployment never recorded. It reports each one rather than
deleting it. To migrate deliberately:

1. Run the deployment once with the tags the device should keep, for example
   `DOTFILES_SKILLS=design,caveman,lark`. A directory that already holds the
   selected bytes is adopted and recorded without a rewrite.
2. Run it again with the desired selection. A recorded directory that leaves
   the selection is pruned from each managed root.
3. A catalog directory whose bytes differ from the pinned copy is preserved and
   reported. Remove that directory deliberately to let the pinned copy replace
   it; keep it if it is device content the catalog does not own.

The deployment never deletes a device-created skill and never follows a
symlink. The report names the skill and the root for every preserved entry, so
the migration is a sequence of reviewed decisions, not a bulk delete.

## The commands

```bash
python3 deployment/update_skills.py check     # the pins, the review, and the CLI drift
python3 deployment/update_skills.py review    # the review alone
python3 deployment/update_skills.py check --library <path>   # measure another library
```

`check` and `review` read the deployed shared tree by default and report the
per-client inventory, the budget findings, and the ratchet result. A library
that cannot be read is reported as not measured; the check never claims a
budget it did not measure. `--report` prints the findings without failing on
them, which is what the deployment does with the library it is about to ship.

The deployment never fails on the review. The gate is the explicit check, and
the reviewer runs it against the library that holds the changed row.
